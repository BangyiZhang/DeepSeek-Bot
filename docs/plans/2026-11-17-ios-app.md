# iOS 版手机 App

- 日期：2026-11-17
- 状态：阶段 0 完成；阶段 1 在模拟器上验过，真机未验
- 相关：上游 Fei2411/DS-Bot#1448（iOS 版需求）、Fei2411/DS-Bot#1004（手机 App 和加密连接，已合并进上游 `dev`）；[手机 App](2026-10-24-mobile-app.md)；上游 `docs/plans/2026-10-24-mobile-api.md`

## 结论

**不从零写 iOS App，也不另起一套协议。** 官方仓库已经有了：

| 部分 | 上游位置 | 现状 |
|---|---|---|
| 手机 App（iOS + Android 同一份代码，Expo React Native） | `mobile/` | Android beta 已发；iOS 代码能编，但从没发过包 |
| 端到端加密连接（Noise、X25519 身份、扫码配对、中转） | `link/src/` | 已上线 |
| 中转服务器（只转发密文） | `link/server/` | 官方 `wss://relay.dsbot.app/v1/link`，可自建 |
| 电脑端（插件里，桌面应用和插件版都有） | `ds-bot/src/host/phone.js`、`mobile.js` | 手机直接调 `api/bot`，和桌面窗口同一套操作 |
| 握手和版本 | `hello` → `api`、`capabilities` | 只加东西不升版本，客户端跳过不认识的 |

所以 iOS 版要做的是：**把上游 `mobile/` 在 iOS 上做完、发出去，并补上 iOS 特有的部分（推送、后台、文件）。** 所有改动按上游的规矩做成 PR 提给 `Fei2411/DS-Bot` 的 `dev`，这样官方仓库和我们的 fork 用的是同一个 App、同一个协议。

不选原生 SwiftUI：要重写约两万行界面，还要把 `link/` 的 Noise 和帧格式移植成 Swift，两套客户端以后每加一个功能都要做两遍。原生只在两处有优势（推送扩展、小组件），这两处用 Expo 的原生模块或 App Extension 就能做，不需要整个 App 原生。

## 结构

```
iPhone (mobile/, Expo RN)                     电脑 (DSH + ds-bot 插件 / 桌面应用)
 ├ 扫码配对：dsbot://pair?server&host&key&code    ├ phone.js：HostLink，只往外连
 ├ RelayTransport → SecureTransport(Noise)       ├ callBot(endpoint, payload) → api/bot
 ├ RpcClient: method "bot" {endpoint,payload}    ├ feedTap → 加密推到已连上的手机
 └ Keychain 存身份私钥                            └ phone.json：身份、已配对手机
          \                                     /
           └──── 中转服务器（link/server，只见密文）────┘
                 ＋ 新增：APNs 推送转发（见下）
```

手机能做的事 = 电脑上 `api/bot` 的所有接口（`phone-*` 配对类除外）。这一点决定了「官方仓库也能用」：

- 官方 `ds-bot` 和我们 fork 的 `ds-bot` 都装了 `phone.js`，同一个 iOS App 都能连。
- fork 独有的功能（比如 Pi Durable 的任务界面）在电脑端照旧加接口；手机端的对应页面按 `hello.capabilities` 里有没有这项来显示。连官方 `ds-bot` 时这些页面自动不出现，不会报错。

## 分阶段

### 阶段 0：fork 跟上上游（前提）

我们的 `main` 包含上游 `main` 的全部提交，但还没有 #1004（`phone.js`、`link/`、完整的 `mobile/`）。上游 `dev` 比我们多约 27 个提交以上。

- 新开 `chore/sync-upstream-mobile`，合并上游 `dev`；`ds-bot/client.js` 冲突取上游再 `npm run build`（同 `scripts/merge-dev.sh` 的做法）。
- fork 自己的桌面应用（`app/`）不用改：手机连接在插件里，打开「设置 → 手机」即可配对。
- 验收：`npm test`、`--check`、`npm run lint`、smoke；Android App 能和合并后的 fork 配对聊天。

### 阶段 1：iOS 能装、能配对、能用（对应 #1448 的四项）

代码上基本已经兼容 iOS（键盘、字体、`AppState` 前后台都有 iOS 分支），缺的是配置和发布：

1. `app.json`
   - 给 `expo-local-authentication` 加插件配置和 `NSFaceIDUsageDescription`。高权限操作要 Face ID，没有这条说明在 Face ID 机型上调用会失败。
   - `expo-image-picker` 的相册说明（`NSPhotoLibraryUsageDescription`）。
   - `ITSAppUsesNonExemptEncryption` 现在是 `false`，但 App 自带 Noise 端到端加密。上架前要按 Apple 的出口合规规则确认，不确定就改成 `true` 并填合规信息，不能照抄。
   - `bundleIdentifier`：官方包用上游的 `io.github.fei2411.dsbot`；自己签的包用自己的 ID，通过环境变量或 `app.config.js` 覆盖，不改仓库里的默认值。
2. 配对：#1448 里用户用**系统相机**扫二维码没反应，是因为手机上没装 App（`dsbot://` 没人认领）。装好以后系统相机也能直接打开 App；App 内扫码（`expo-camera`）照旧是主路径。可以在电脑的配对页加一句「iPhone 请先安装 App，再用 App 扫码」。
3. 构建和分发（选一种，不互斥）：
   - **自己用**：`npx expo run:ios --configuration Release --device`，免费 Apple ID 签名 7 天有效，付费开发者账号 1 年。
   - **TestFlight**：需要开发者账号（99 美元/年），`eas build -p ios` + `eas submit`，或本机 Xcode Archive。官方包由维护者的账号发。
   - 自签 IPA 说明写进 `mobile/README.md`，满足 #1448 里「自签也行」的需求。
4. 在 iOS 上过一遍 Android 已经修过的那批问题（连接器、记忆页、设置页、Markdown 图片），这些是共享代码，大多数已经修好，重点看 iOS 独有的：键盘遮挡、安全区、深色模式、iPad 横屏（`supportsTablet: true`）。

模拟器上的结果（2026-11-17，iPhone 17 Pro、iOS 26.5、Xcode 26.6）：

- **启动即崩**：Expo SDK 58 默认用预编译模块，预编译的 `ExpoFileSystem` 引用了当前 `ExpoModulesCore` 没有的符号（dyld `Symbol not found`）。CI 只编译不启动，所以没发现。修法：`expo-build-properties` 里 `ios.usePrecompiledModules: false`，全部从源码编。
- **一直转圈**：`CODE_SIGNING_ALLOWED=NO` 的包没有钥匙串权限，`SecureStore` 报「A required entitlement isn't present」。是编译方式的问题，`npm run ios` 会签名；写进了 `mobile/README.md`。
- 演示团队、侧栏、审批卡、深色模式正常。用户消息里的文件卡片被挤成一列（共享代码，Android 也一样），已修。
- 本机中转（`ws://127.0.0.1:8787`）+ 测试台：用 `dsbot://pair` 链接配对成功；手机发、电脑回；App 退到后台 35 秒、电脑发消息，回到前台能补齐。
- 没验到：模拟器连着 Mac 键盘时不弹软键盘，键盘遮挡要真机看；Face ID 和相机扫码要真机。
- 自签安装说明写在 `mobile/README.md`；`DS_BOT_IOS_BUNDLE_ID` 覆盖 bundle id，不改仓库默认值。

验收：iPhone 真机上扫码配对 → 团队和群列表 → 私聊和群聊收发（含图片）→ 审批和提问卡 → 后台再回来能补齐。

### 阶段 2：推送（iOS 最大的缺口）

iOS 在 App 进后台约 30 秒后就会挂起 WebSocket。现在的设计是「回到前台用 `notices(since, boot)` 补齐」，补齐没问题，但**用户在外面时根本不知道 Bot 在等审批**——这正是手机 App 最主要的用途。

两份已定的设计在这点上不一致：`mobile-app` 说要做端到端加密的推送，`mobile-api` 说不做系统推送。改已定设计要维护者点头，所以这一阶段**先在 #1448 里提方案，等维护者同意再做**。建议的做法：

1. 手机配对后，用 link 的新方法 `push-register` 把 APNs device token 交给电脑（不走 `api/bot`：`phone-*` 接口手机调不了），同时把 token 登记到中转服务器。
2. 电脑端有 `approval`、`question`、`view`、`message`、`done` 提醒且这台手机**不在线**时，用手机的公钥把提醒（`{ kind, name, title, text }`）加密，交给中转服务器。
3. 中转服务器用 APNs 发 `mutable-content: 1` 的通知，正文只有密文和占位文字「DS Bot 有新消息」。
4. 手机上的 **Notification Service Extension** 从共享 Keychain（App Group）取私钥解密，换成「Chief 请你审批：……」。点通知打开对应的 Bot 或群。
5. Android 走 FCM，同一套密文格式。

代价和风险：

- 中转服务器要持有 APNs 证书（.p8）。官方中转由维护者配置；自建中转的人要用自己的开发者账号和自己签的 App，否则推不了。没配 APNs 的中转照旧工作，只是没有推送。
- Notification Service Extension 在 Expo 里要用 config plugin 加一个原生 target，这是 `mobile/` 里第一段 Swift 代码。
- 中转服务器能看到「什么时候推了几条」，看不到内容。

### 阶段 3：iOS 体验（可选，按需做）

- 文件和图片存到手机、分享出去（#1443）：iOS 用分享面板（`expo-sharing`）。
- 从别的 App 分享文字、图片给某个 Bot：Share Extension。
- 正在跑的长任务：Live Activity 显示进度；锁屏小组件显示「需要你」的数量。

## 怎么让官方仓库也能用

- 每个阶段一个 PR，进上游 `dev`：分支 `feat/1448-ios-app`、`feat/1448-ios-push`，按 PR 模板写，`Fixes #1448`，Changelog 写在模板里。
- 协议只加不改：新接口、新提醒种类都写进 `capabilities`，旧 App 连新电脑、新 App 连旧电脑都照常工作。
- fork 独有的东西不进上游 PR；在 fork 里加，靠 `capabilities` 隔开。
- 阶段 1 以后 fork 不再单独维护 `mobile/`，定期从上游合并，避免两份 App 分叉。

## 测试

- 不用真 key：电脑端照旧用 `ds-bot/dev/mock-llm.mjs` 和 test bench（`.dsh-test-<name>/`），不碰 `~/.dsh` 和桌面应用的数据。
- 本机起一个中转：`cd link && PORT=8787 npm run server`，在「设置 → 手机」里填 `ws://localhost:8787/v1/link`；iOS 模拟器能直接访问电脑的 localhost。
- 只看界面：`EXPO_PUBLIC_DSB_DEMO=1` 用演示团队，不用配对。
- 推送只能在真机上测；APNs 用 sandbox 环境。

## 不做什么

- 不在手机上跑 Agent，不在手机上存聊天记录（和已定设计一致）。
- 不做原生 SwiftUI 重写。
- 不改 DSH，不依赖 DSH 安装目录里的文件。
