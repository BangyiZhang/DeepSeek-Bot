# Local macOS application update controller

The user explicitly requested an in-app development/build/install loop for this fork. DSH stays unchanged. This is a local macOS installer, separate from GitHub releases and the existing download updater.

Dev builds in the checkout with a reproducible preparation command. It saves validation results and the candidate ASAR hash, then calls `request_desktop_update` from its own user-requested Bot chat. The tool only queues a handoff; it cannot choose the installed target, run arbitrary commands, change data locations or increase privileges. A worker session, group chat or background report cannot install an application.

Electron validates the local bundle's signature, identity, executable architecture and evidence, copies it to a unique sibling staging directory, and verifies the staged copy. It keeps a snapshot of its own runtime and copies a dependency-free installer into an owner-only job directory. Electron launches that installer as a detached Node-mode process, with no IPC/stdio dependency on the Host. The installer waits for an explicit armed marker and the original Electron PID to exit. Electron waits for the Bot response, queued work, active agents/jobs, group work and unfinished durable tasks to become idle before arming and quitting. A busy or unknown Host blocks installation.

The controller journals phases before renames, keeps the previous app as a sibling backup, launches the replacement, and requires a job-specific receipt with the launched PID and expected ASAR hash. The replacement writes that receipt only after its Host and Bot UI are ready. Timeout or launch failure terminates only the replacement process owned by the controller, restores the verified previous bundle and relaunches it. The controller never kills the original app to force an update. Incomplete journal recovery restores the known old app rather than replaying unknown work.

The runtime snapshot is independent of the installed target; changing or rolling back that target cannot replace the installer's code while it is running. Copy-on-write copying limits transient disk use. Old backups are removed only after confirmed success. Failed recovery preserves evidence and recoverable files. A crashed controller can be rerun from its job directory; no persistent system daemon or elevated helper is installed.

A native result and `get_desktop_update` expose durable status. The restarted plugin claims a completion report before admitting one notification to the originating Bot, avoiding blind resend after an uncertain report admission. The install receipt remains queryable even if report delivery is interrupted. Provider secrets, DSH contents and environment dumps never enter the job manifest or logs. Normal application startup continues using the same user data.

Validation uses isolated fake app trees for destructive failure cases and a real packaged app with throwaway data and a loopback mock for restart acceptance. No mock task is sent to the user's real team. The initial version containing the controller is installed once externally; later user-requested updates use the in-app tool.

Implementation references: [Node detached child processes](https://nodejs.org/api/child_process.html#optionsdetached) and [Electron Node mode](https://www.electronjs.org/docs/latest/api/environment-variables#electron_run_as_node). The worker uses no inherited IPC or output pipes. Runtime and deployment remain separate bundles until the worker exits.

Validation on macOS arm64: plugin tests 1117 passed / 2 skipped, desktop tests 135 passed / 1 skipped, all 52 mock Host smoke steps, generated client check, lint and packaged chat/selection check passed. The real packaged acceptance traversed queued → prepared → controller_ready → waiting_exit → swapping → launching → completed, verified different old/new PIDs and the exact-hash UI receipt, and found one completed report in the saved originating chat. Destructive failure, ambiguous ownership, controller locks and rollback are tested against isolated filesystem fixtures; the live packaged acceptance covers the successful restart path. Electron Node-mode regression also verifies raw ASAR hashing/copying. No real user profile was a test target.

Bundle I/O uses Electron's documented [original-fs interface](https://www.electronjs.org/docs/latest/tutorial/asar-archives#treating-an-asar-archive-as-a-normal-file), while copying the helper's own source out of ASAR uses its virtual file reader. Readiness uses the team's actual work view: the `live` map also caches idle conversation entries and must not itself be treated as an active-task count.
